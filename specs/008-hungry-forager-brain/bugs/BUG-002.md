# Bug Report: Forager fly never stops to eat, so hunger, taste and brain activity look dead

**Type**: Untested flow (primary); Spec gap for the panel bars and the activity view
**Severity**: High
**Feature**: Hungry Forager Brain (`008-hungry-forager-brain`)
**Reported**: 2026-10-05
**Status**: Patched (brake fix skipped by the user; metabolism and taste fixed; SC-011 still open)
**Patched**: 2026-10-05
**Decision**: Add FR-031 to FR-034 and SC-011 to SC-013. Calibration uses an eating criterion. The brake is diagnosed before any change.
**Fix**: T108–T116 new; T063, T096, T100 reopened. Browser checks (T109, T111, T115) open. The SC-011 50% threshold is proposed and to be confirmed in `calibration.md`.

## Description

Reported while running the forager world (`public/world/world-forager.json`, `flies.brain.version` `v1`). Five symptoms,
which are related but not all one defect:

1. **Hunger not shown.** The side panel does not show the fly's hunger. The user asks for it as bars from 0 to 100%.
2. **Fly never pauses at food.** The fly only moves; it never stops on a flower and eats (US2 scenario 1 never fires).
3. **Taste neurons show no activity.** The taste inputs stay at 0 in the panel.
4. **Brain activity point cloud is too quiet.** It does not show enough activity to compare with the simple brain.
5. **Unclear whether the brain works.** Nothing in the app tells the user whether the forager brain behaves correctly.

Symptoms 2 and 3 are linked (see Root Cause). Symptoms 1, 4 and 5 are partly spec gaps: 008 states no requirement for
the bars, the activity view or an end-to-end check.

## Root Cause Analysis

Not confirmed in a browser. The following is from the code and the recorded calibration.

**Why the fly never pauses (symptom 2).** `canEat` needs `body.speed < food.eatSpeed` (0.5 tiles/s in
`world-forager.json`), and `body.speed` is distance over `dt`. The top speed is `maxSpeed` = 3 tiles/s, so the net drive
(`forward − backward`) must fall to about 0.17 on a flower. The world does not hold the fly (FR-026), so the brain must
brake by itself. `calibration.md` shows that the brain rarely does this:

- In the calibration grid, 15 of 16 settings have **0 eating bouts**. The one with eating (`synapticScale` 50,
  `tauAdapt` 20, `adaptStep` 0.05) has 348 bouts and 447 eating ticks across 30 flies over 3,000 ticks each. That is
  about 15 eating ticks per fly per run.
- `calibration.md` says the highest find rates (83–87%) "never eat, so the fly walks through flowers without stopping."
  This is the same symptom the user sees. The selected setting was chosen because it was the only one that eats, but
  the bar it cleared is very low, and it was not checked against the speed rule.
- `eatSpeed`, `feedThreshold`, `consumeRate`, `regrowth` and `antennaOffset` were not searched. Only the LIF parameters
  and the adaptation terms were.

So the likely cause: the brain's forward and backward outputs do not fall to near zero on a flower, so `speed` stays
above `eatSpeed`. Whether this is the LIF calibration, the drive mapping (`applyForagerMotor` reads `forward` and
`backward` by name), or the `eatSpeed` value is not yet known. The `stepForagerBody` sign test (FR-019) passes, which
makes a turning error unlikely, but it does not check the brake.

**Why taste is silent (symptom 3).** `senseForagerFly` sets taste to `flowers.fraction(cx, cy)` only when
`isStimulusCell(cx, cy)`. Taste is therefore non-zero only while the fly stands on a flower cell. A fly that never
stops on a flower gives 0 taste on nearly every tick. This matches FR-025, so the spec is followed and the symptom is a
consequence of symptom 2. Not verified: whether any tick in the calibration runs had a fly on a flower cell at all.

**Why the hunger bar is not visible (symptom 1).** The code writes the bars. `action.js` shows the Energy and Hunger rows
for any fly whose history entry has `energy` set, and `model.js` takes both from the last entry. The bars therefore
should appear for a v1 fly. Possible reasons, none confirmed: the user is looking at a v0 or mock fly; the Action
section is not in the pane the user checks; or the bars are at their starting value (energy 0.3, hunger 0.7) and do not
move, since the fly never eats and metabolism is only 0.01 per tick. The 0–100% scale itself is not in the spec.

**Why the point cloud is quiet (symptom 4).** Not investigated in code yet. Brightness comes from `record.activity`
via `neuron-map.js` (changed by BUG-001). The v1 spike rates are low (the calibration shows low activity), and the
view has no requirement or test for how readable the activity is. This is a spec gap as much as a defect.

**Why it is unclear the brain works (symptom 5).** The verification steps for this feature are open: T075 (panel label
check), T097 (Gate B timing), T102 (quickstart run, no `quickstart-run.md`) and T107 (browser check of the activity view).
The app has no on-screen diagnostic, so the user cannot see the eating-related values.

**Classification.** The primary defect is an untested flow: nothing verifies that the shipped forager world makes a
hungry fly brake and eat, and calibration accepted a setting that barely does it. Symptoms 1, 4 and 5 are spec gaps.
No implementation error has been proven. The code matches FR-019, FR-023, FR-025 and FR-026 as written.

## Headless Diagnosis (T111, 2026-10-05)

Run without a browser, through the same `stepForagerFly` the browser uses, with the shipped `world-forager.json` and
its `brains/forager-brain.brain`, 3,000 ticks, six flies per seed. Only seeds 101, 6 and 7 were run (the scratch script
is not in the repo). Per seed, flies that reached a flower with stock above 0:

| Seed | Flies | Reached a flower | Flies that ate | Speed on a flower (lowest seen) | Feed on a flower (highest seen) | Mean forward on a flower |
|---|---|---|---|---|---|---|
| 101 | 6 | 2 | 0 | 2.85 and 3.00 | 1.00 | 0.99 and 1.00 |
| 6 | 6 | 3 | 0 | not recorded | not recorded | not recorded |
| 7 | 6 | 2 | 0 | 2.15 | 1.00 | 0.99 |

What this shows:
- The feed output does rise above the threshold (0.5) on a flower. The forward output stays near 1 at the same time.
- The fly crosses the flower at full speed (3 tiles/s, `maxSpeed`), so `speed < eatSpeed` (0.5) never holds.
- The body rule itself is doing what FR-019 says: forward minus backward sets the speed. The brake is missing in the
  brain's drives, not in the body's arithmetic.
- Energy is 0 at the end of every run. The fly starts at 0.3 and loses `metabolism` (0.01) per second, so it is empty
  after about 30 s of run time. A fly that cannot eat stays at hunger 1, so the hunger bar sits at 100%. This is a second
  issue for T112 to settle.

Not yet checked in the browser (T111 open): the same numbers in the panel, and whether the panel bars move.

## Held-Out Run (T110, 2026-10-05)

`tests/slow/forager-brake.test.mjs`, all 30 held-out seeds (101–130), six flies per seed, 3,000 ticks, the real v1
brain: 180 flies, 76 reached a flower with stock above 0, and 2 of those 76 ate (3%). SC-011 needs at least 50%.
The run took about 3.5 minutes, so it is kept out of `npm test`.

A second check (SC-012) fails: at least one eating tick has taste input 0. The cause is the order inside a tick.
`senseForagerFly` reads taste from the cell the fly stands on before it moves, while `applyForagerMotor` decides
eating from the cell after the move. A fly that steps onto a flower and eats in the same tick has taste 0 for that tick.
This is a small timing defect, separate from the brake, and needs a decision on which cell taste is sampled from.

## Connectome Check for a Brain-Path Brake (T112 prep, 2026-10-05)

The chosen fix is a brain-path change: a feed-to-forward inhibitory pathway in the extraction. Before changing the
extractor, the traced connectome (`connectome-weights-…-traced-only.feather`, `body-neurotransmitters`, sign table as in
`extract/configs/forager-brain.json`, confidence ≥ 0.5) was checked for that motif:

- MN9 (feed) has 350 upstream partners; DNp09 (forward) has 705 inhibitory upstream partners (GABA or glutamate).
- 10 neurons are both feed-upstream (excitatory) and forward-inhibitory. That is a direct candidate for a brake: active
  feed, reduced forward.
- The current extraction selects interneurons by flow within a budget of 1,500 per odour and taste pool. Nothing forces
  those 10 neurons into the selection, so the shipped brain may not contain them.

Not done yet: changing the selection to include these neurons, a new extraction (SC-001 range 2,000–6,000 neurons,
Gate A), a headless diagnosis, and re-calibration. The selection change alters the extraction contract
(`contracts/extract-config-forager.md`) and the forager artifact, so it needs the user's go-ahead before it starts.

1. Confirm the root cause in the browser first: open `public/world/world-forager.json` from a static server, select a
   v1 fly, and log `speed`, `feed`, `forward`, `backward` and `eating` per tick while it is on a flower. Record the
   numbers in `bugs/BUG-002.md`. This settles whether the brake is missing (LIF, drive mapping) or `eatSpeed` is too low.
2. Run `/speckit.bugfix.patch` to update the spec artifacts:
   - Add a requirement that the panel shows energy and hunger as 0–100% bars for a v1 fly (FR-004 extension).
   - Add a success criterion that a hungry fly placed on a flower in `world-forager.json` brakes below `eatSpeed` and
     eats in the held-out run, with a stated minimum.
   - Add a requirement for the activity view's readability (SC-010 extension), and a diagnostic line for the selected fly.
   - Reopen T063 and T096, and record the tracking fix for T100.
3. Run `/speckit.bugfix.verify` to confirm consistency.
4. Resume `/speckit.implement` to apply the fix: re-calibrate with the eating criterion (T096), then fix the brake in
   `public/js/fly/forager-step.js` or the calibration values, and complete T102 and T107.


## Fix Attempt and Wrap-Up (2026-10-05)

Kept:
- **Metabolism** 0.01 → 0.005 per second (`public/world/world-forager.json`, `public/js/fly/fly-config.js`,
  `contracts/world-config-forager.md`). An empty-start fly from 0.3 now reaches 0 in about 60 s.
- **Taste timing**: `applyForagerMotor` (`public/js/fly/forager-step.js`) reads the cell the fly stood on before the
  move, the same cell where taste was sensed. Eating, consumption and the bout use that cell. Regression test:
  `tests/taste-timing.test.mjs`.

Skipped by the user's decision: the brake fix. The extraction `brake` rule (a feedforward motif from the connectome)
was built, tested and run. It stopped all forward drive in the headless probe (the feed output is near-constant, so
the brake is always on), so it was reverted and is not in the repo. The shipped brain
(`public/brains/forager-brain.brain`) and its config are unchanged.

Consequence: SC-011 still fails (3% of flies that reached a flower ate, against 50% required). The fly still does not
brake on food. The taste part (SC-012) holds on the eating ticks of the held-out run. Calibration (T096, T100, T116) was
not re-run. This bug is open for a later feature, not closed by this wrap-up.
