# Bug Report: `outputScale` is shared across every output channel, so lowering it to fix `forward` also starves `feed`

**Type**: Spec gap (the single-scale design is a deliberate, documented scoping decision — ADR 004's own "Open
questions" flagged the risk this report confirms; the spec's Assumptions carried that scoping forward without a
fallback)
**Severity**: High
**Feature**: Output-pool synaptic scale (`010-output-pool-synaptic-scale`, ADR 004)
**Reported**: 2026-10-07
**Status**: Patched
**Patched**: 2026-10-07

## Description

ADR 004's `outputScale` ([lif-v1.js](../../../public/js/brain/lif-v1.js),
[fly-brain-v1.js](../../../public/js/brain/fly-brain-v1.js)) applies one number to every neuron in every declared
output channel alike — `forward`, `backward`, `turn-left`, `turn-right`, and `feed` — because the mechanism only
tracks "is this neuron in any output pool," not which one. With the shipped `outputScale: 5`
([world-forager.json](../../../public/world/world-forager.json)), navigation improved as intended (`forward`/
`turn-*` are no longer pinned near the firing ceiling), but the same 10× cut also suppressed `feed`, which had no
real headroom to spare — it previously crossed `feedThreshold` (0.5) only because of the over-excitation this
change removed. Confirmed on the live world's own seed (`config.seed = 1990`, all 6 flies, 214 on-flower ticks
over 12,000 ticks): `feed`'s on-food mean is 0.333 and its observed maximum is 0.452, never reaching 0.5, and a
fly reported sitting over food for an extended stretch accrued zero energy. The fix is to make `outputScale`
resolve per declared output channel (accept a plain number, applied as today, or an object keyed by channel id,
e.g. `{"feed": 30, "forward": 5}`, with a channel absent from the map falling back to `synapticScale`) so
`forward`/`turn`/`backward` can stay at the value that fixed navigation while `feed` gets its own independent
scale to search for a working on-food/off-food dynamic range — a value that has not yet been tried, since every
sweep so far (ADR 004 Annex A.2) varied `synapticScale`/`tauAdapt` with no per-channel decoupling at all.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — "A brain's output pools can be scaled independently of its interneuron
  bulk" (P1, the feature's only story).
- **Affected requirements**:
  - **FR-001**/**FR-003**: both are written as "an independent scale for synapses whose target neuron is declared
    as an output neuron" — singular, one scale for the whole output set. They do not distinguish between output
    channels, so they are satisfied as written but do not cover this failure mode.
  - **FR-004**/**FR-007**: "generic...by neuron role membership, not by referencing specific named outputs" — a
    per-channel extension must preserve this: it needs to key by channel id (data already on
    `capabilities.channels.outputs[*].id`), not hand-reference `"forward"`/`"feed"` in code.
- **Gap identified**: the spec's own **Assumptions** section states plainly: *"All output channels share one scale
  in this feature (per the ADR's own scoping decision). Giving individual output channels (e.g. `forward` vs.
  `feed`) their own independent scales is explicitly out of scope and left as potential follow-on work."* That
  follow-on work is now required — the single shared scale cannot satisfy both `forward` (needs the cut) and
  `feed` (cannot tolerate the same cut) simultaneously, confirmed by live measurement, not just predicted.

### plan.md

- **Affected sections**: **Summary** ("a second LIF-core parameter, `outputScale`...that replaces `synapticScale`
  only for edges whose target is a declared output-role neuron" — one parameter, one value) and **Scale/Scope**
  ("One new parameter (`outputScale`) and one new per-neuron mask (`outputMask`...)").
- **Impact**: the plan's Technical Context, Project Structure, and Constitution Check were all written for a
  single scalar `outputScale`. A per-channel design changes the shape of the parameter (scalar or `{channelId:
  number}` map) and the shape of the derived structure (`outputMask` sized to neuron count stays, but it must now
  resolve to *which* channel's scale a target belongs to, not just "is an output"). This needs a new/amended plan
  before implementation, not a direct code patch — `createNetwork`'s contract and the LIF-key validation in
  `validate.js` both assume `lif.<key>` values are plain numbers today.

### tasks.md

- **Affected tasks**: T008 (`LIF_V1_DEFAULTS` gains `outputScale: null`), T009 (`resolveParams` validation), T010
  (`outputMask` built from `graph.outputNeurons`, binary membership only — no per-channel distinction), T011
  (`step`'s single-branch scale selection), T012 (`fly-brain-v1.js` flattens all output channels into one
  `outputNeurons` list, discarding channel identity in the process).
- **False completions**: none — T008–T012 are marked `[X]` and correctly implement the single-scale mechanism the
  spec and plan describe. They are not wrong; the design they implement is now known to be insufficient for the
  `feed` channel's actual operating point.
- **Missing tasks**: none yet — this report is the trigger for `/speckit-bugfix-patch` to add them (per-channel
  `outputScale` resolution in `lif-v1.js`/`fly-brain-v1.js`, the `validate.js` shape change for an object-valued
  `lif.outputScale`, new `tests/lif-v1.test.mjs`/`tests/validate-flies.test.mjs` cases, and a contract amendment to
  `lif-v1.md`).

## Root Cause Analysis

This is not an implementation defect — T008–T012 match ADR 004's design exactly, and `tests/lif-golden.test.mjs`
plus the new `L6` tests all pass. The root cause is that ADR 004 itself flagged this as an open risk and the spec
carried it forward as an accepted scope limit rather than a resolved question. The ADR's own **Open questions**
section asks: *"Is per-role granularity (one scale for all output channels) enough, or will `forward` and `feed`
eventually need separate scales? ... smaller follow-on if the joint sweep can't satisfy both pools at once."* The
spec's Assumptions then restated that limit as a settled scoping decision without a trigger condition for
revisiting it. The shipped calibration (`outputScale: 5` in `world-forager.json`) was set directly in the world
file without a corresponding dated entry in `specs/008-hungry-forager-brain/calibration.md` recording the sweep
and its held-out verdict, as ADR 004's own "Recalibration protocol" (steps 2–5) requires — so the joint
`(synapticScale, outputScale)` search that would have surfaced this `feed`-starvation trade-off before shipping
was not completed or recorded. The live-world measurement in this report is the evidence that the open question
resolved the unfavorable way: one scale is **not** enough for both pools at once.

## Recommended Fix

1. Run `/speckit-bugfix-patch` to update `spec.md` (replace the single-scale Assumption with a per-channel
   requirement; add an acceptance scenario for differing channel scales), `plan.md` (the parameter becomes scalar
   **or** an object keyed by output-channel id, with per-channel fallback to `synapticScale`), and `tasks.md` (new
   tasks for `lif-v1.js`'s per-channel resolution, `fly-brain-v1.js`'s channel-aware `outputNeurons` construction,
   `validate.js`'s shape handling, and contract/test updates).
2. Run `/speckit-bugfix-verify` to confirm consistency across the updated artifacts.
3. Resume `/speckit-implement` to apply the code fix, then re-run the ADR's Recalibration protocol (this time
   recording the sweep and held-out verdict in `calibration.md` per its own step 5) to find a working
   `feed`-specific scale — e.g. starting from the untried higher end (`outputScale.feed` around 20–30) while
   holding `outputScale.forward`/`turn`/`backward` at the already-validated 5.
