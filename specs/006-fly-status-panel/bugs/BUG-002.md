# Bug Report: Panel re-renders on every tick, flickers, and rebuilds the brain map

**Type**: Spec gap (primary), with implementation drift
**Severity**: High
**Feature**: Fly Status Side Panel (`006-fly-status-panel`)
**Reported**: 2026-10-05
**Status**: Patched
**Patched**: 2026-10-05

## Description

The fly status panel refreshes too often, and the brain activity map is unreliable.

- **Safari**: the brain activity map (three.js point cloud) does not render, and the panel flickers because it refreshes very often.
- **Chrome**: the brain activity map renders, but the panel also refreshes very often.
- **When it broke**: during the implementation of feature 006, when the panel started to follow fly ticks.

Expected behaviour, as the user states it:

1. A tick must not re-render the whole panel. Only the values that changed should update (numbers, bar widths, point colours). The screen must not flicker.
2. "Expensive" objects, such as the brain map (WebGL renderer, scene, geometry, orbit controls), must be built once per selected fly. They must stay alive across ticks and must not be destroyed and rebuilt by a refresh.

### What the code does today

- In commit `4cefd62` (feature 006), `main.js` called `renderPanel(...)` from `onFlyUpdate`. That is once per tick of **any** fly: 6 flies × 20 Hz ≈ 120 full panel renders a second. FR-012 then read "the panel MUST update on each tick of the selected fly", and the code did not even filter by the selected fly.
- Commit `ddd437a` (feature 007) added a partial fix outside the 006 artifacts. Ticks now mark the panel stale, and a 200 ms timer re-renders it (`PANEL_INTERVAL_MS`, `public/js/main.js:29`, `:171-181`). FR-012 in `spec.md` was reworded at the same time. No bug report or task records this change. The refresh is still a **full** render of every section:
  - `renderChannelRows` calls `container.replaceChildren(...)` and builds new rows on every refresh (`public/js/ui/panel/channels.js:9-11`). Inputs and Outputs are thrown away and rebuilt 5 times a second.
  - The Action section writes `body.textContent` on every refresh (`public/js/ui/panel/sections/action.js:7`), even when the text has not changed.
  - The neuron map calls `cloud.resize()` and `cloud.update()` on every refresh, and the panel also runs its own `requestAnimationFrame` loop (`public/js/ui/panel/sections/neuron-map.js:17-24`, `:50-62`). Two update paths draw the same canvas.
- The point cloud is **not owned by a lifecycle** that ends when its DOM goes away. `disposeMount` is called only when a new fly is mounted into the *same* body element (`neuron-map.js:29-30`). Several paths drop the canvas without disposing its WebGL context:
  - `renderFly` replaces the whole `.readout` when the selected fly changes (`public/js/ui/panel/panel.js:183-186`). The new readout has new section bodies, so the old mount is never found or disposed.
  - `showMessage` replaces the Fly pane when the selection is cleared (`panel.js:177-180`).
  - A section error or an `error` fly status writes `body.textContent` or removes the section boxes (`panel.js:188-192`, `:208-209`), which drops the canvas.
  - Each such path leaves a live `WebGLRenderer` and `OrbitControls` attached to a detached canvas. The next render creates a new one.
- Safari limits the number of live WebGL contexts per page more tightly than Chrome, and it drops the oldest one when the limit is reached. Leaked contexts, plus a new context each time a mount is rebuilt, are the likely reason the map stays blank in Safari while Chrome still draws it. This is a hypothesis to confirm in Safari's console ("Too many active WebGL contexts" / context lost warnings). It is consistent with the code paths above.
- While the World tab is shown, the Fly pane is `hidden`. The neuron map still receives `update()` calls and its rAF loop, and `resize()` returns early on a 0×0 box. A hidden map keeps drawing for no one.

## Artifact Traceability

### spec.md

- **Affected user story**: Story 2 — See Which Brain Neurons Were Recently Active (the map must show recent activity, scenarios 1 and 2). Story 1 — See the Selected Fly's Status Beside the World (the panel frame, SC-006). Stories 3 and 4 (the channel rows that are rebuilt on each refresh).
- **Affected requirements**:
  - **FR-012**: originally "The panel MUST update on each tick of the selected fly, and MUST NOT block the world from drawing." This is the requirement that caused the per-tick full render. It was reworded in commit `ddd437a` (feature 007) to "refresh at least 5 times a second … MUST NOT follow every tick, because re-rendering it at the tick rate flickers in Safari". The rewording sets a rate, but it still does not separate a structural render from a value update. The change has no BUG entry and no `**Bugfix**` footer in `spec.md`.
  - **FR-003 / FR-005**: the neuron map must show brightness from spikes. The spec does not say that the map is a long-lived object that is built once per selected fly.
  - **SC-003**: "A neuron that spikes becomes visibly brighter within one second." This fails in Safari, where the map does not draw.
  - **SC-006**: "the world keeps drawing at its normal frame rate while the panel updates." A full panel rebuild 120 (later 5) times a second, with flicker, goes against the intent.
- **Gap identified**:
  - The spec has no requirement that a tick updates only values in place, and that the panel structure (tabs, list, section boxes, rows, canvas) is built only on a structural change: a fly selected, a tab switched, a section added or removed, or a fly status changed to error.
  - The spec has no requirement on the lifetime of expensive objects. It does not say that the brain map is created once per selected fly, kept across ticks and tab switches, and disposed exactly once when the fly is deselected or replaced.
  - The spec has no "no visible flicker" criterion and no browser matrix for the panel. The plan lists Safari as a target, but no success criterion checks it.
  - The spec does not say whether hidden content (the Fly pane while the World tab is shown) keeps updating.

### plan.md

- **Affected sections**:
  - Technical Context → **Performance Goals** ("The panel refreshes 5 times a second (FR-012)") and **Target Platform** ("Evergreen browsers (Chrome, Firefox, Safari) with WebGL"). Safari is a stated target, but nothing checks the WebGL context budget.
  - Technical Context → **Constraints** ("Only the selected fly's brain is drawn, so the three.js scene is one object at a time"). The code does not hold this: leaked mounts leave more than one WebGL context alive.
  - Key Design Decision **5** (panel sections behind a registry). The section contract has only `render(container, model)`. It has no `mount`, `update` or `dispose` step.
  - Key Design Decision **4** (fade envelope). The neuron map has two drawing paths (the refresh and its own rAF loop) with no single owner.
  - Project Structure: `public/js/main.js`, `public/js/ui/panel/panel.js`, `public/js/ui/panel/channels.js`, `public/js/ui/panel/sections/neuron-map.js`, `public/js/viz/point-cloud.js`.
  - `contracts/panel-sections.md`: "Mounting is decided once per fly … When the selected fly changes, the mounted set is recomputed." It does not define unmount or disposal.
- **Impact**:
  - The section contract needs a lifecycle: `mount(container, model)` once per fly, `update(model)` per refresh that changes values in place, and `dispose()` called by the shell whenever the section's DOM is removed (fly change, deselection, error, tab teardown).
  - The shell (`panel.js`) needs to own the section instances per selected fly and to call `dispose` on every path that removes their DOM.
  - The panel refresh in `main.js` should only call `update` on mounted sections. Structural events (select, tab, layer toggle, fly error) call the structural render.
  - The neuron map should have one draw owner: its rAF loop, which runs only while the Fly tab is visible and some neuron is fading. The refresh only records that new spikes exist.
  - `channels.js` should build the rows once per fly and update the bar widths and numbers in place.
  - The plan should record the Safari WebGL context limit as a constraint: at most one point cloud context alive at any time.

## Root Cause Analysis

The root cause is in the spec. The original FR-012 asked the panel to "update on each tick", and the section contract (`render(container, model)`) has only one operation. With one operation, every tick has to re-run the whole render. The implementation went further and rendered on every tick of every fly, about 120 times a second.

Three implementation gaps make it worse:

1. **No value-only update path.** Rows and text are rebuilt instead of updated, which causes the flicker. Safari shows it most.
2. **No disposal lifecycle.** The neuron map's WebGL context is freed only when a new fly is mounted into the same body element. Readout replacement, deselection and errors leak contexts. Safari's lower limit on live WebGL contexts explains why the map is blank there and still visible in Chrome.
3. **Two draw paths for one canvas.** The refresh and the section's own rAF loop both draw the map, and both keep running while the pane is hidden.

Feature 007 reduced the rate to 5 Hz and reworded FR-012, but it did not fix the structure. The change was made outside the 006 bug workflow, so `tasks.md` and the plan do not show it.
