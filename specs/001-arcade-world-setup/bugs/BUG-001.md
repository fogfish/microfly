# Bug Report: Misaligned terrain tiles leave dark edge pixels

**Type**: Dependency issue (primary), with a Spec gap (contributing)
**Severity**: High
**Feature**: 001-arcade-world-setup (Arcade World Setup)
**Reported**: 2026-10-04
**Status**: Fixed (headless verification done; manual check T026/T034 open)
**Patched**: 2026-10-04
**Assessment**: [`.specify/bugs/tile-edge-misalignment/assessment.md`](../../../.specify/bugs/tile-edge-misalignment/assessment.md) · analysis: [`sheet-analysis.md`](../../../.specify/bugs/tile-edge-misalignment/sheet-analysis.md)

## Description

Rock fields and water show the same dark edge tile repeated in every cell. Dark stripes and stray transparent pixels appear at tile boundaries, so the terrain does not look like a real landscape.

The reporter's rule: `roguelike-16.png` is organised into tile groups. When a tile from a group is used, its surrounding tiles must come from the same group. The world must be pixel perfect and aligned with real landscapes, and the attribution must be updated to reflect the groups.

Measured on the shipped `public/world/world.json`:
- `rock` (sheet 102,238 = tile (6,14)) is an edge tile of rock block A. Its bottom row is 0% opaque, and it has dark outlines on the N, W and E sides. It is used on every rock cell.
- `water` (sheet 17,51 = tile (1,3)) has dark outline pixels on the N and E sides. The clean interior tile is `water` (0,0).
- `grass` (sheet 0,255 = tile (0,15)) has 6–12% transparent edge pixels.
- The renderer never fills a cell with an opaque base before drawing its sprite. Transparent pixels therefore show the dark page background (`--bg`) or the previously drawn cell.

## Artifact Traceability

### spec.md
- **Affected user story**: Story 1 — Explore a Retro Arcade World in the Browser (P1)
- **Affected requirements**: FR-001 (pixel-art style, consistent with classic 90s arcade games), FR-005 (element types visually distinct)
- **Gap identified**: The spec requires pixel-art terrain that is recognisable, but it does not require terrain tiles to be placed consistently with their tile groups. It also has no requirement for seam-free or edge-correct terrain. The Assumptions section says the art "may be reused", with no condition on how the tiles connect. Nothing defines "looks like a real landscape" as a testable criterion.

### plan.md
- **Affected sections**: Summary (technical approach), Technical Context → Rendering (sprites from sheet, drawn per cell), Project Structure (`render/renderer.js`, `world/generate.js`), Research link R2 and R6
- **Impact**: The plan has no step that chooses tiles by neighbour. `generate.js` assigns one terrain id per cell, and the design does not model tile groups, edge roles, or a base fill under terrain. The plan needs:
  - a tile-group model in the config (or a documented equivalent),
  - a neighbour-based pick step after terrain placement,
  - an opaque base under every terrain cell,
  - a decision on integer-only zoom for pixel-perfect rendering.

  - **T019**: marked done. The renderer draws transparent edges over an unfilled canvas, which the plan did not forbid, but which lets background pixels into the scene.
  - **T037**: marked done. `ATTRIBUTION.md` lists single tile coordinates only. It has no group names, roles or neighbour rules, so it does not record the sheet's structure as the reporter asked.
  - **T017**: marked done. Generation has no neighbour rule, so it cannot satisfy the group rule.
- **Missing tasks**:
  1. Analyse `roguelike-16.png` groups: list each group, its tiles, the role of each tile (edge/corner/fill), and whether it is opaque. Record the result in `public/assets/ATTRIBUTION.md` and in a sheet-group section of `contracts/world-config.md`.
  2. Add a tile-group field to `world.json` (for example `groups` with named roles per terrain), with validation that every role points to a real sprite.
  3. Add a neighbour-based autotile pick to `generate.js` (8-neighbour, same-group only), keeping the PRNG draw order so the seed contract (FR-013) still holds.

## Root Cause Analysis

Mainly a dependency assumption that was wrong. Research R2 confirmed that the Kenney sheet contains grass, water and rock tiles, and treated each tile as an independent single-tile sprite. The sheet is actually built from autotile groups in which edge tiles only work next to their own group. The assumption was never tested against the tiles' edges.

The spec has a gap that let it through. FR-001 asks for pixel art but not for seam-free or group-consistent terrain, so the task list had nothing that would catch this. The plan follows the research, so it has no neighbour step.

This is not a regression in code that matched the spec. The code does what the plan describes. The plan is incomplete for the tileset it chose.

Confidence: high for the tile choice (measured per-edge opacity and outline, see `sheet-analysis.md`). Medium for the transparency-over-background mechanism, which is the likely reason the stripes look dark rather than just repeated.

## Fix and verification (2026-10-04)

- **Fix**: rock is drawn as an overlay on an opaque grass base. Each rock cell's edge tile is picked from its neighbours (`public/js/world/autotile.js`). Group data is in `world.json` (`groups.rock`). Cell edges are rounded to whole device pixels in `renderer.js`.
- **Headless Chrome, zoom 2 and zoom 1.7**: rock shows rounded edges with no dark stripes or repeated edge lines. Grass is clean. Console shows only the expected `fire` shortfall warning.
- **Tests**: `npm test`, 42 of 42 pass (`tests/autotile.test.mjs`, `tests/validate.test.mjs`).
- **Limitations**: water has no shore (square opaque tile on grass). The three-open rock junctions use a fallback tile. See `public/assets/ATTRIBUTION.md`, Known limitations.
- **Still open**: a person should check the look at zoom 0.5 to 4 (T026). Integer-only zoom was not adopted (T046 superseded by device-pixel rounding, to confirm).
