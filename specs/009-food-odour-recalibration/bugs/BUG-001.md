# Bug Report: One Food Object Per Class Cannot Reach the Wanted Odour Coverage

**Type**: Spec conflict
**Severity**: High
**Feature**: 009-food-odour-recalibration (`009-food-odour-recalibration`)
**Reported**: 2026-10-07
**Status**: Patched
**Patched**: 2026-10-07

## Description

The shipped map has exactly three edible food objects, one per size class (`small` = `red_flower_plant`,
`medium` = `jungle-plant-010`, `large` = `jungle-plant-015`), as `FR-001` requires. `scripts/food-placement.mjs 6`
measures the resulting odour-free share of walkable cells at 49.8% (`results.md` line 78), i.e. about 50.2% odour
coverage.

The reporter wants multiple food instances per size class — several `small` units, several `medium` units, several
`large` units — so that odour coverage rises to roughly 60–70% of the map. Placing instances of the same class near
each other is explicitly allowed as a way to raise the local odour level (overlapping falloffs add, which the spec's
own Edge Cases section already describes for two sources).

This is not something the current spec, data model, validator or world files can express: they are built around the
closed rule "exactly one food object per size class," enforced in three independent places (spec requirement,
contract, and validator code). Adding instances conflicts with that rule as written, not with any missing detail.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — *Food Smells Stronger the Bigger It Is* (P1), User Story 2 — *Odour Is
  Patchy, So the Fly Has Somewhere to Go* (P2).
- **Affected requirements**:
  - `FR-001` (line 125): "The world MUST contain exactly three edible food objects: one small..., one medium..., and
    one large.... They are the only edible objects in the world." — directly contradicts the request for multiple
    instances per class.
  - `FR-006` (line 135): "Between 30% and 70% of walkable cells MUST have an odour value of zero." — expressed as
    odour-*free* share, not odour-*coverage*. The reporter's target (60–70% coverage ⇒ 30–40% free) already falls
    inside this range numerically, but the spec gives no requirement for the mechanism (multiple instances, placed
    near each other) that the reporter wants to use to get there.
  - `FR-008` (line 138): "No food object MUST stand on water, on a blocked cell, or on a cell that another food
    object occupies." — this rule already permits distinct food objects to sit on different, nearby cells. It is
    compatible with "multiple instances nearby," but the spec never defines what an "instance" of a size class is
    once there can be more than one per class, so `FR-008`'s per-object checks (and the per-class `kind` key used
    everywhere else) do not carry over cleanly.
  - **Edge Cases** (line 112): "What happens when two food objects' odour regions overlap? The values add... and
    the peak stays at the stronger object's position." — written for the three *different* class objects, but the
    same mechanics are what the reporter wants applied *within* a class.
- **Gap identified**: The spec's `Assumptions` section anticipated exactly this change and reserved it explicitly:
  line 195, "`'Only three edible objects' means exactly one food object per size class... If several objects per
  size were meant, FR-001 and FR-006 change and the spec is revisited.`" That reservation is now triggered. `FR-001`
  must change from "exactly three" to "one or more per class," the **Key Entities** definition of *Food unit* (line
  169, "One of three edible objects") must change, and `FR-006`/`SC-002` need a restated target (the reporter's
  60–70% coverage, i.e. 30–40% odour-free, is narrower than today's 30–70% free band and should be made explicit
  rather than left as a coincidental subset) alongside a rule for how close same-class instances may sit (the
  "nearby, to raise local odour" allowance needs the same kind of bound `FR-008` gives today, or two instances could
  be placed on the same cell by mistake).

  `public/world/` (each file described as carrying exactly one `large`/`medium`/`small` entry at a fixed position).

  was built assuming one cell per kind drives one stimulus region per kind. Supporting several instances per class

  `kind`) or a new per-instance id is introduced, and how `fly-world.js`'s stimulus map and `food.js`'s `points()`
  aggregate odour across same-class instances that sit close enough for their reaches to overlap (today's
  `odour-reach.md` contract covers summing across *different* sources already — Edge Cases line 112 — so this is
  additive, not a rewrite, but it is unplanned).

## Root Cause Analysis

This is a changed requirement, not an implementation error. Spec 009 deliberately scoped "three edible objects" as
"one per size class" (`Assumptions`, line 195) and built the whole pipeline — world file schema, validator, layout
cell-to-kind mapping, placement script, and tests — on that closed cardinality. The spec's own Assumptions section
flagged this as the most likely point of revision ("If several objects per size were meant, FR-001 and FR-006
change and the spec is revisited"), and the reporter's request is precisely that trigger. The resulting ~50% odour
coverage measured in `results.md` is the correct, intended outcome of the one-per-class design — it is not a defect
in that design, it is a design that the reporter now wants replaced with a denser one.
