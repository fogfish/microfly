# Bug Report: Fly Sprite Has No Male/Female Variants, and Wing Orientation Doesn't Match Reference Anatomy

**Type**: Spec gap
**Severity**: Low
**Feature**: 009-food-odour-recalibration (`009-food-odour-recalibration`)
**Reported**: 2026-10-07
**Status**: Patched
**Patched**: 2026-10-07

## Description

The reporter supplied `fruit-fly.jpeg` (a dorsal-view reference diagram contrasting female and male *Drosophila*,
untracked at the repo root) as the anatomical basis for the fly sprite art, and asked for two changes:

1. **Sex-differentiated sprites.** The reference shows a female fly (longer, broader abdomen with evenly spaced dark
   bands to the tip) and a smaller male fly (shorter body, a solid dark terminal abdomen band/tip) as two distinct
   shapes. The shipped sprite set has only one fly silhouette (`fly`) plus a colour-only `fly-baseline` variant
   (`public/world/world.json` `sprites.fly` / `sprites['fly-baseline']`) — there is no male or female sprite, and no
   `sex` concept anywhere in the fly code (`grep -rn "sex\|female\|male" public/js/fly/*.js` returns nothing).
2. **Wing angle.** In the reference image, each wing extends laterally from the thorax, roughly perpendicular (a
   right angle) to the body's long axis. In the shipped `fly` pixel grid (`public/world/world.json`
   `sprites.fly.pixels`), the `w` (wing) pixels run down both sides of the body for rows 8–23, parallel to the
   body's long axis rather than spread out to the sides — the wings read as a border folded flat along the abdomen,
   not as a pair sticking out at a right angle the way the reference draws them.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 4 — *The Fly Looks Like a Fruit Fly* (P3), lines 101–117. Acceptance Scenario
  2 depends on a reviewer recognizing "the wings" at a glance — a wing silhouette that reads as a stripe down the
  body rather than a projecting pair works against that scenario.
- **Affected requirements**:
  - `FR-014` (line 183): "The fly sprite MUST look like a fruit fly... a pair of clear wings..." — says wings must
    exist but gives no shape or angle, so there is no requirement the current parallel-to-body wing art violates on
    paper, even though it doesn't match the reporter's reference.
  - `FR-016` (line 185): "The baseline fly sprite MUST use the same 32 by 32 shape and differ only in colour..." —
    this requirement is written for exactly one shape with one colour-only variant (the existing calibration
    baseline). It does not anticipate a second axis of variation (sex) that changes *shape*, not colour, and as
    written it would conflict with adding `fly-female`/`fly-male` shapes unless re-scoped.
  - **Key Entities → Fly sprite** (line ~211): "The 32×32 image of the fly. Attributes: the normal sprite and the
    baseline sprite." — only two attributes/ids are defined; there is no `sex` attribute and no third/fourth sprite
    id.
- **Gap identified**: The spec was written for one fly shape with a calibration colour swap, and never considered
  sex as a dimension of the fly sprite. `FR-014` needs a wing-orientation clause (wings project laterally, at
  roughly a right angle to the body axis, as in the reference), and a new requirement is needed for female/male
  sprite pairs (e.g., "the fly sprite MUST have a female and a male variant, distinguished by body/abdomen shape per
  the reference anatomy, each with its own baseline colour variant"). `FR-016` needs to be re-scoped so "differ only
  in colour" applies within a sex (female normal vs. female baseline, male normal vs. male baseline), not across the
  whole sprite set. Key Entities' *Fly sprite* needs a `sex` attribute alongside the existing normal/baseline
  attribute.

### plan.md

- **Affected sections**: Summary item 6 ("Fly sprite becomes a 32 × 32 pixel grid drawn as a fruit fly... drawn
  unrotated"), the D2 decision note (rotation only; no mention of sex), and the Project Structure listing of
  `contracts/fly-sprite.md` ("32 × 32 fly and baseline sprites").
- **Impact**: The plan assumed exactly two sprite ids (`fly`, `fly-baseline`) feeding `flies.sprite` /
  `flies.baselineSprite` in world config, with the host (`public/js/fly/`) never asked to pick between shapes. Adding
  sex needs the plan to say whether sex is: (a) a new pair of sprite ids referenced by new world-config keys (e.g.
  `flies.femaleSprite`/`flies.maleSprite`, each with its own baseline), with sex assigned to each fly at spawn; or
  (b) folded into the existing `sprite`/`baselineSprite` keys with the world config choosing per-population mix.
  Either way this touches `public/js/render/sprites.js` (loads sprites from the `sprites` map — unaffected, it is
  shape-agnostic) and whichever part of `public/js/fly/` currently reads `flies.sprite` to decide what a given fly
  instance draws (today a single, unconditional choice).

## Root Cause Analysis

This is a spec gap, not implementation drift. `FR-014`/`FR-016` and `contracts/fly-sprite.md` were written for a
single generic fly silhouette with one calibration-only colour swap (`fly` vs. `fly-baseline`), which was sufficient
for User Story 4 as scoped (P3, purely visual, "look like a fruit fly," no sex requirement). The reporter is now
asking for a second, previously unconsidered dimension — sex — modeled on a specific anatomical reference image, plus
a wing-orientation detail (`FR-014` never specified an angle) that the existing pixel art happens to get wrong
relative to that reference. Nothing in `T034`/`T035`/`T036` was implemented incorrectly against the spec that
existed when they were done.
